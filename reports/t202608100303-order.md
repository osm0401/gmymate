# 목표 설정·운동 알림 MVP — 작업 지시서

## 목표

로그인 사용자가 운동 목표를 수정하고, 선택한 요일·시각에 운동하지 않았을 때 알림을 받도록 한다.

두 기능을 한 PR에 넣지 않는다. 아래 순서대로 각각 구현·리뷰·병합한다.

| 순서 | 브랜치 | 기능 | 담당 |
|---|---|---|---|
| PR 1 | `fe/goal-settings-mvp` | 목표 설정·수정 | `[FE]` |
| PR 2 | `fe/workout-reminder-mvp` | 앱 활성 상태 운동 알림 | `[FE]` |

현재 Codex 역할은 `api/**`만 수정할 수 있으므로 직접 구현하지 않고 FE에 넘긴다. `api/**`, DB 스키마, Composer 의존성은 두 PR 모두 변경하지 않는다.

착수 전 다음 조건을 해결한다.

- 현재 작업 트리에 필수 문서인 `docs/collab/roles.md`, `decisions.md`, `backlog.md`, `handoffs.md`가 없다. 다른 브랜치의 오래된 문서를 그대로 복사하지 말고 실제 기준 브랜치에 맞는 버전을 복구한다.
- 현재 브랜치와 `fe/frontend-refactor`의 모듈 구조가 다르므로 배포 기준 브랜치를 확정한다. 아래 파일 경로는 현재 체크아웃의 ES Module 구조를 기준으로 한다.
- 복구된 `roles.md`에서 FE 브랜치·담당 규칙을 재확인한 뒤 백로그에 두 작업을 별도 항목으로 등록한다.

PR 1의 사용자 약속:

- `목표 유형`, `목표 몸무게`, `주간 운동 횟수`를 로그인 후 수정할 수 있다.
- 저장 즉시 요약과 주간 달성률에 반영되고 기존 동기화로 보존된다.

PR 2의 사용자 약속:

- 알림 사용 여부, 시각, 요일을 설정할 수 있다.
- 앱이 열려 있거나 다시 활성화될 때 조건을 확인해 하루 한 번 알린다.
- 오늘 운동했거나 이번 주 목표를 이미 달성했다면 알리지 않는다.

이번 알림 MVP는 앱이 완전히 종료된 상태의 백그라운드 푸시를 보장하지 않는다. 종료 상태 Web Push가 필수 요구라면 PR 2를 시작하지 말고 PWA·VAPID·구독 API·발송 스케줄러를 별도 기능으로 설계한다.

비범위:

- 자유 텍스트·복수 목표·목표 마감일
- AI 운동 추천과 자동 목표 조정
- 이메일·SMS·카카오 알림
- Service Worker, PWA 설치, 서버 Web Push, cron·queue
- 전체 프로필 편집과 동기화 충돌 해결

## 리서치 근거 (검색으로 확인한 사실 + 왜 이 방식을 택했는지)

- 저장소에는 이미 `gmymateProfile.goal`, `targetWeight`, `weeklyWorkout`과 주간 게이지·달성 축하가 구현돼 있다. 결손은 “가입 이후의 목표 편집”이다. 현재 `main.html`의 수정 링크는 `onboarding.html`로 이동하지만, 온보딩 제출은 항상 `signup.php`를 호출하므로 기존 사용자는 정상 수정할 수 없다.
- 알림도 `workoutAlert` 토글과 18시 이후 `new Notification()` 호출이 존재한다. 그러나 앱 초기화 때 한 번만 검사하고 `sessionStorage`로 탭 단위 중복을 막기 때문에 예약 알림이 아니다. 완료 운동이 기록으로 이동한 뒤 현재 운동 배열이 비워지는 구조도 오알림을 만들 수 있다.
- 프로필과 설정은 이미 `api/sync.php`의 계정별 JSON 스냅샷으로 동기화된다. 새 목표·알림 테이블을 추가하면 동일 데이터의 진실 원천이 둘로 갈리므로 이번 MVP는 `gmymateProfile`과 `gmymateSettings`를 재사용한다.
- Fitbod는 주간 운동 횟수 또는 특정 요일을 설정하고 선택적으로 알림을 받으며, 같은 목표를 주간 진행률·스트릭 계산에 사용한다. gmymate도 기존 주간 목표를 유지하면서 알림 요일·시각만 추가하는 방식을 택한다. [Fitbod Weekly Workout Goal, Previews & Streaks](https://help.fitbod.me/hc/en-us/articles/360013245993-Weekly-Workout-Goal-Previews-Streaks)
- Apple Fitness는 요일별 목표, 주간 리뷰, 목표 일시 중지까지 지원한다. 이는 성숙 기능이므로 이번 PR에서는 단일 주간 목표와 알림 일정만 구현한다. [Apple Fitness 목표 조정](https://support.apple.com/en-ca/guide/iphone/iph9a08e004e/ios)
- 알림 권한은 사용자 클릭 같은 명시적 제스처 안에서만 요청해야 하며 HTTPS가 필요하다. 콜백형 `Notification.requestPermission(callback)`은 deprecated이므로 Promise 형식을 사용한다. 또한 `new Notification()`은 대부분의 모바일 브라우저에서 `TypeError`가 발생할 수 있어 예외 처리와 앱 내 알림 대체가 필요하다. [MDN Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)
- iOS/iPadOS의 실제 Web Push는 16.4 이상에서 홈 화면에 설치된 웹 앱과 Service Worker가 필요하다. 현재 저장소에는 manifest와 Service Worker가 없으므로 종료 상태 푸시는 이번 범위에서 제외한다. [WebKit Web Push 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- 2026-08-10 기준 PHP Web Push 라이브러리 `minishlink/web-push` 최신판은 `11.0.0`이며 PHP 8.2 이상과 여러 확장이 필요하고 Packagist 등록 advisory는 0건이다. v11은 PSR-18 기반으로 변경된 breaking release다. 이번 PR에서는 이 라이브러리를 추가하지 않는다. [Packagist](https://packagist.org/packages/minishlink/web-push), [v11 릴리스 노트](https://github.com/web-push-libs/web-push-php/releases/tag/v11.0.0)
- 닷홈은 PHP 8.2를 지원하지만 실제 계정 버전과 확장은 현재 저장소에서 검증할 수 없다. 향후 Web Push PR에서는 이를 먼저 확인해야 한다. [닷홈 웹호스팅 안내](https://manual.dothome.co.kr/manual/info/44)

### PR 2 — 앱 활성 상태 운동 알림

기존 설정을 다음 계약으로 확장한다.

```json
{
  "workoutAlert": true,
  "workoutAlertTime": "18:00",
```

## 수용 기준 (Acceptance Criteria) — 검증 가능한 형태로

### PR 1

1. 로그인 사용자는 회원가입 화면으로 이동하거나 `signup.php`를 호출하지 않고 목표를 수정할 수 있다.
2. 유효한 목표 유형, 목표 몸무게, 주간 횟수를 저장하면 홈 요약과 주간 게이지가 즉시 갱신된다.
3. 새로고침·재로그인 후에도 값이 유지되고, 성공적인 서버 동기화 뒤 다른 기기에서도 동일하게 보인다.
4. 허용되지 않은 목표 유형, 29.9kg, 250.1kg, 소수 둘째 자리, 주 1회·6회는 거절된다.
5. 저장 전후 키·나이·현재 체중·경력·운동 기록·설정·인바디·루틴 데이터가 동일하다.
6. 저장 공간 오류가 발생하면 기존 목표가 유지되고 거짓 성공 메시지가 나타나지 않는다.
7. 목표 로직의 lines/branches/functions 커버리지가 각각 80% 이상이며 전체 Node 테스트가 통과한다.
8. PR diff에 `api/**`, DB 스키마, 외부 런타임 의존성 변경이 없다.

### PR 2

1. 기본값은 OFF이고 페이지 로드만으로 알림 권한 창이 나타나지 않는다.
2. 사용자가 직접 켰을 때만 권한을 요청하며 거부 시 ON 상태를 저장하지 않는다.
3. 선택하지 않은 요일이나 설정 시각 전에는 알림이 발생하지 않는다.
4. 앱을 설정 시각 전에 열어두어도 시각이 되면 조건을 다시 평가한다.
5. 앱이 백그라운드에 있다가 설정 시각 이후 다시 보이면 즉시 조건을 평가한다.
6. 오늘 완료된 운동 세션이나 진행 중 완료 세트가 있으면 알림이 발생하지 않는다.
7. 이번 주 완료 일수가 주간 목표 이상이면 알림이 발생하지 않는다.
8. 같은 계정·기기·현지 날짜에는 새로고침해도 한 번만 알리고, 다음 날에는 다시 알릴 수 있다.
9. 권한 거부, API 미지원, `new Notification()` 예외에서도 앱의 다른 기능은 정상 동작한다.
10. 알림 설정은 재로그인·동기화 후 유지되지만 마지막 표시 날짜는 다른 기기로 동기화되지 않는다.
11. Chrome/Firefox 데스크톱과 모바일 에뮬레이션에서 설정·허용·거부·완료 억제 흐름을 검증한다.
12. 앱 종료 상태에서는 알림을 보장하지 않으며 UI·문서·PR 설명 어디에서도 백그라운드 푸시로 표현하지 않는다.
13. 알림 로직의 lines/branches/functions 커버리지가 각각 80% 이상이고 전체 검사에 실패·skip된 신규 테스트가 없다.
14. PR diff에 Service Worker, Web Push 서버, VAPID 키, cron, `api/**` 변경이 없다.

## 예상 리스크

- 기준 브랜치에 따라 ES Module과 `window.Gmymate` 구조가 달라진다. 잘못된 브랜치에서 구현하면 큰 충돌과 기능 중복이 생긴다.
- `user_data`는 전체 JSON을 last-write-wins로 덮으므로 여러 기기에서 동시에 목표나 설정을 바꾸면 다른 데이터가 유실될 수 있다.
- 동기화는 저장 후 1.5초 지연되며 실패를 조용히 무시한다. 저장 직후 앱을 닫으면 다른 기기에 반영되지 않을 수 있다.
- 브라우저는 백그라운드 탭의 타이머를 지연한다. 따라서 정각 보장은 할 수 없고 화면 복귀 시 재평가가 필수다.
- 알림 권한을 거부한 뒤에는 브라우저 설정에서 직접 변경해야 할 수 있다. 반복 권한 요청을 시도하면 안 된다.
- 기기 시간대가 바뀌면 같은 설정 시각이 새 현지 시각으로 해석된다. 서버 기준 예약이 필요한 경우 Web Push 후속 기능에서 IANA 시간대를 도입한다.
- 현재 동기화 API는 임의 JSON 구조를 저장할 수 있으므로 읽을 때마다 목표·설정을 정규화해야 한다.
- 기존 `users.id`와 일부 FK `user_id` 타입이 다르다. 이번 PR은 새 테이블을 만들지 않지만 후속 Push 스키마 전 운영 DB 타입을 확인해야 한다.
- Git에서 제외된 로컬 OAuth 설정에 실제 형식의 비밀값이 존재한다. 기능 PR에 포함하지 말고 유효 여부 확인·회전·환경변수 이전을 별도 보안 작업으로 처리한다.
- 종료 상태 알림 요구가 뒤늦게 추가되면 단순 확장이 아니라 PWA·구독 보안·스케줄러·만료 구독 정리가 필요한 별도 아키텍처 작업이다.
