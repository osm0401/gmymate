# 나만의 루틴 추가 — 작업 지시서

## 목표

로그인 사용자가 오늘 구성한 운동 목록에 이름을 붙여 저장하고, 루틴 탭에서 다시 시작하거나 삭제할 수 있게 한다.

- 담당: `[FE]` Claude, 리뷰·테스트: Gemini
- 브랜치: `fe/custom-routine-mvp`
- 저장 단위: `{ id, name, exerciseIds }`
- 한도: 사용자당 30개, 루틴당 운동 1~12개
- 백엔드: 기존 `api/sync.php`의 사용자별 JSON 동기화를 재사용하며 신규 API·테이블을 만들지 않는다.
- 비범위: 세트·중량·횟수·휴식시간 저장, 루틴 편집·공유·즐겨찾기·주간 일정·AI 추천·사용자 정의 운동

현재 체크아웃을 구현 기준으로 삼는다. 단, 배포 기준이 로컬 `main`의 `src/features/routines.js` 포함 상태라면 기능이 이미 있으므로 신규 구현을 중단하고 검증·테스트 작업으로 전환한다. 크게 분기된 `5007997` 커밋을 통째로 cherry-pick하지 않는다.

## 리서치 근거 (검색으로 확인한 사실 + 왜 이 방식을 택했는지)

- 현재 저장 폼과 내 루틴 영역은 `main.html`에 있고, 렌더·삭제·시작 코드도 일부 존재한다. 빠진 것은 폼 제출 처리, 최초 렌더, `gmymateCustomRoutines` 동기화 연결이다. 따라서 새 화면보다 이 연결부를 완성하는 것이 가장 작은 PR이다.
- Strong은 현재 또는 완료한 운동을 템플릿으로 저장하고 재사용한다. 이는 gmymate의 기존 “오늘 구성한 운동을 루틴으로 저장” 흐름과 일치한다. [Strong 템플릿 안내](https://help.strongapp.io/article/105-about-templates)
- Hevy는 루틴을 재사용 가능한 계획, 워크아웃을 실제 수행 기록으로 구분하고 루틴에서 새 워크아웃을 시작한다. 따라서 루틴 시작 후의 기록 변경은 원본 루틴을 수정하지 않아야 한다. [Hevy 루틴과 워크아웃](https://help.hevyapp.com/hc/en-us/articles/33703513582871-Workouts-vs-Routines-in-Hevy-What-They-Mean-and-How-to-Use-Them)
- Fitbod도 현재 운동을 이름 있는 Saved Workout으로 저장한다. 과거 기록 저장과 자동 중량 조정은 성숙 기능이므로 후속 PR로 남긴다. [Fitbod Save a Workout](https://help.fitbod.me/hc/en-us/articles/6259258835863-Save-a-Workout)
- 저장소에는 `package.json`이나 `composer.json`이 없다. 바닐라 ES Modules, PHP/PDO, Web Storage만 사용하므로 신규 라이브러리는 필요 없다.
- `localStorage`는 동기식이며 용량 초과 시 `QuotaExceededError`, 정책 제한 시 `SecurityError`가 발생할 수 있다. 작은 루틴 목록에는 충분하지만 저장 실패를 처리해야 한다. [MDN Web Storage](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API), [MDN 저장소 한도](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- `innerHTML`은 deprecated가 아니지만 XSS 주입 지점이다. 루틴명은 `textContent`로 넣거나 기존 `escapeHtml()`을 모든 텍스트·속성에 적용해야 한다. 별도 sanitizer 패키지는 도입하지 않는다. [MDN innerHTML 보안 경고](https://developer.mozilla.org/en-US/docs/Web/API/Element/innerHTML), [OWASP DOM XSS 예방](https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html)
- 2026-08-10 기준 PHP 최신 안정 패치는 보안 릴리스인 8.5.9다. 이번 PR은 PHP를 변경하지 않지만 운영 환경은 지원 중인 PHP 브랜치의 최신 보안 패치인지 확인한다. [PHP 8.5.9 릴리스](https://www.php.net/releases/8_5_9.php), [PHP 지원 버전](https://www.php.net/supported-versions.php)

## 세부 작업 체크리스트

- [ ] 기준 브랜치가 실제 배포 코드인지 확인한다. 로컬 `main`의 완성형 빌더가 기준이면 구현을 중복하지 않는다.
- [ ] `[REVIEW]` 담당이 먼저 `tests/custom-routines.test.mjs`에 실패 테스트를 작성한다.
- [ ] `src/core/routines.js`에 순수 함수로 루틴 생성·정규화 로직을 둔다.
  - 이름은 trim 후 1~40자만 허용한다.
  - 운동 ID는 `exerciseCatalog` allowlist와 대조한다.
  - 중복 ID는 첫 항목만 유지하고 표시 순서를 보존한다.
  - 손상된 값은 무시하고 최대 30개/12개 한도를 적용한다.
  - 운동명은 저장하지 않고 카탈로그에서 다시 계산한다.
- [ ] `src/features/routines.js`를 추가해 기존 렌더·삭제 코드를 `main.js`에서 이동한다.
  - “루틴으로 저장” 클릭 시 현재 운동이 없으면 폼을 열지 않고 안내한다.
  - 저장 폼을 열고 이름 입력란에 포커스한다.
  - 제출 시 새 배열을 만들어 저장하고 성공 후 폼을 초기화한다.
  - 저장·삭제 실패 시 성공 토스트나 화면 변경을 하지 않는다.
  - 최초 setup에서 저장된 루틴을 즉시 렌더한다.
- [ ] `src/app.js`에서 새 루틴 모듈을 import하고 setup한다.
- [ ] `src/features/main.js`에서는 중복된 렌더·삭제 코드를 제거하고 기존 탭 이동 및 `gmymate:start-routine` 위임만 유지한다.
- [ ] `src/features/workout-log.js`의 루틴 시작 로직을 보강한다.
  - 기존 오늘 기록은 그대로 보존한다.
  - 기존 기록과 중복되는 운동은 추가하지 않는다.
  - 남은 12개 슬롯까지만 저장 순서대로 뒤에 추가한다.
  - `push`, `unshift`, `splice` 대신 `map`, `filter`, spread로 새 배열을 만든다.
  - 일부 운동이 한도로 제외되면 그 사실을 토스트로 알린다.
- [ ] `src/core/sync.js`의 `SYNCED_KEYS`에 `gmymateCustomRoutines`를 추가한다.
- [ ] 계정 A의 로컬 데이터가 계정 B에 노출되지 않도록 동기화 소유자 키를 추가한다.
  - `pullSync(user.username)`으로 현재 소유자를 전달한다.
  - 소유자가 바뀌면 동기화 대상 키를 먼저 비운 뒤 서버 데이터를 적용한다.
  - 로그아웃 시 동기화 대상 로컬 데이터를 정리한다.
  - 세션 토큰이나 비밀번호는 `localStorage`에 저장하지 않는다.
- [ ] `src/styles/workout-log.css`와 `src/styles/main.css`에 저장 폼과 카드 액션에 필요한 최소 스타일만 추가한다.
- [ ] 사용자 입력은 raw `innerHTML`로 삽입하지 않는다. 기존 문자열 렌더를 유지한다면 모든 동적 값을 `escapeHtml()` 처리한다.
- [ ] 신규 API, DB 마이그레이션, npm/composer 의존성을 추가하지 않는다.
- [ ] `scripts/check.ps1`과 아래 커버리지 검사를 통과시킨다.

```powershell
node --test --experimental-test-coverage `
  --test-coverage-include=src/core/routines.js `
  --test-coverage-lines=80 `
  --test-coverage-branches=80 `
  --test-coverage-functions=80 `
  tests/custom-routines.test.mjs

.\scripts\check.ps1
```

- [ ] 모바일 브라우저에서 저장 → 새로고침 → 시작 → 삭제 흐름을 검증하고 PR에 결과를 기록한다.
- [ ] 리뷰 전 `.env`, `api/config.php`, 공급자 설정 파일 등 ignored 자격증명이 diff에 포함되지 않았는지 확인한다.

## 수용 기준 (Acceptance Criteria) — 검증 가능한 형태로

1. 오늘 운동이 0개이면 루틴 저장이 거절되고 `gmymateCustomRoutines`가 변경되지 않는다.
2. 공백 제거 후 1~40자인 이름과 유효한 운동 1~12개를 저장하면 현재 표시 순서가 보존된다.
3. 공백 이름, 40자 초과 이름, 카탈로그에 없는 운동만 포함한 입력은 저장되지 않는다.
4. 같은 이름의 루틴은 허용되며 31번째 루틴은 명시적 안내와 함께 거절된다.
5. 저장 직후 “내 루틴” 카드가 보이고 새로고침 후에도 동일하게 나타난다.
6. 루틴 시작 시 기존 오늘 기록은 삭제되지 않으며, 중복되지 않은 운동만 12개 한도 내에서 저장 순서대로 추가된다.
7. 시작된 운동의 수정·완료·삭제는 저장된 원본 루틴을 변경하지 않는다.
8. `<img src=x onerror=alert(1)>` 같은 루틴명은 문자로만 표시되고 요소 생성이나 스크립트 실행이 발생하지 않는다.
9. 손상된 JSON, 잘못된 객체, 삭제된 운동 ID가 있어도 유효한 루틴만 표시되고 앱 전체가 중단되지 않는다.
10. `localStorage.setItem()`이 `QuotaExceededError` 또는 `SecurityError`를 던지면 실패 안내가 표시되고 거짓 성공 상태가 남지 않는다.
11. 삭제 시 선택한 루틴만 제거되고 마지막 루틴 삭제 후 “내 루틴” 섹션이 숨겨진다.
12. 저장 후 1.5초 이상 기다린 뒤 같은 계정의 다른 브라우저에서 새로고침하면 루틴이 복원된다.
13. 같은 브라우저에서 계정 A가 로그아웃하고 계정 B가 로그인하면 A의 루틴이 보이거나 B의 서버 데이터로 전송되지 않는다.
14. 신규 순수 로직의 lines/branches/functions 커버리지가 각각 80% 이상이고 `scripts/check.ps1`이 테스트를 SKIP하지 않고 PASS한다.
15. PR diff에는 `api/**`, DB 스키마, 외부 의존성, 자격증명 파일 변경이 없다.

## 예상 리스크

- 현재 체크아웃과 로컬 `main`이 초기 커밋 이후 크게 분기돼 있다. 잘못된 기준 브랜치에서 구현하면 기능 중복이나 대규모 충돌이 발생한다.
- 서버 동기화는 계정당 JSON 전체를 last-write-wins로 덮는다. 여러 기기에서 동시에 수정하면 루틴 또는 다른 기록이 유실될 수 있으며, 병합·버전 충돌 해결은 별도 PR로 남긴다.
- 저장 직후 1.5초 이내 종료하면 서버 push가 실행되지 않을 수 있다. 이 PR은 로컬 보존과 다음 정상 저장만 보장하고 영속 재시도 큐는 후속 범위로 둔다.
- 첫 배포 시 기존 로컬 데이터에는 소유자 표식이 없어 어느 계정 데이터인지 완전히 판별할 수 없다. 마이그레이션 정책을 PR 설명에 명시해야 한다.
- `file:` URL에서 `localStorage` 동작은 브라우저별로 정의되지 않는다. 검증은 로컬 HTTP 서버 또는 실제 HTTPS 환경에서 수행한다.
- 세트·중량·횟수까지 기억할 것으로 사용자가 기대할 수 있다. 이번 PR은 운동 구성만 저장한다는 문구를 유지하고 상세 처방 저장은 후속 기능으로 분리한다.
