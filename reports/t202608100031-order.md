## 리서치 근거 (검색으로 확인한 사실 + 왜 이 방식을 택했는지)

- 저장소는 빌드 도구와 `package.json`이 없는 바닐라 HTML/CSS/ES Module 구조다. 인바디 데이터는 `gmymateInBodyLogs`의 `{ date, weight, muscleMass, bodyFat }` 형태로 저장되고 기존 동기화 대상에도 포함된다. 따라서 백엔드나 데이터 마이그레이션 없이 프론트엔드에서 파생 그래프를 만들 수 있다.
- 현재 작업 브랜치의 `src/features/inbody.js`에는 직접 SVG를 생성하는 프로토타입이 이미 있으나, `main`에는 인바디 모듈 자체가 없다. 또한 프로토타입은 여러 기능이 섞인 `1120d27` 커밋에 포함돼 있다. **해당 커밋 전체를 병합하지 말고**, 인바디 기록 계약이 이미 존재하는 정식 기준 브랜치에서 그래프 변경만 추출한다.
- InBody 공식 자료는 체성분 이력에서 몸무게·골격근량·체지방률을 점 그래프로 추적하며 최근 8회와 전체 이력을 구분한다. 이번 PR은 기존 기록 목록과 모바일 가독성을 고려해 최근 8회만 채택한다. 전체 기간 전환은 별도 기능으로 남긴다. [InBody 체성분 이력 설명](https://qr.inbody.com/ri/770/adult/en)
- Withings도 최근 8회 측정값을 추이 화면의 기본 범위로 사용한다. 최신값 대비 변화량도 제공하지만, 이번 명령의 범위를 넘으므로 추가하지 않는다. [Withings Body+ 화면 설명](https://support.withings.com/hc/en-us/articles/219027767-Body-What-screens-can-be-displayed-on-my-scale)
- 2026-08-10 검색 기준 주요 후보는 Chart.js `4.5.1`, D3 `7.9.0`이다. 두 지표의 단순 꺾은선 그래프에는 범용 라이브러리가 과하며, 현재 저장소의 무빌드·오프라인 우선 구조와 기존 SVG 프로토타입을 고려해 **외부 의존성 없는 SVG 구현**을 선택한다. [Chart.js 4.5.1](https://github.com/chartjs/Chart.js/releases), [D3 7.9.0](https://github.com/d3/d3/releases)
- Chart.js 4는 ESM 중심으로 변경됐고 기존 `dist/chart.min.js`, `xAxes`/`yAxes`, `destroy` 훅 등 과거 예제와 호환되지 않는다. 레거시 Chart.js `<2.9.4`에는 prototype pollution 취약점도 있었다. 이번 PR에서 라이브러리를 도입하지 않아 버전·공급망·폐기 API 위험을 없앤다. [Chart.js 4 마이그레이션](https://www.chartjs.org/docs/latest/migration/v4-migration.html), [CVE-2020-7746](https://github.com/advisories/GHSA-h68q-55jf-x68w)
- `toISOString()`은 UTC를 사용하고 `new Date("YYYY-MM-DD")`도 날짜 전용 문자열을 UTC로 해석한다. 현재 프로토타입 방식은 시간대에 따라 기본일이나 표시일이 하루 어긋날 수 있으므로 로컬 날짜 키와 문자열 분해 방식으로 교체한다. [MDN `toISOString()`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date/toISOString), [MDN Date 문자열 해석](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date)
- W3C는 차트를 복합 이미지로 보고 동등한 텍스트 설명을 제공하도록 권고한다. SVG에 접근 가능한 이름과 요약을 제공하고, 기존 기록 목록을 원자료 대안으로 유지한다. [W3C 복합 이미지 접근성](https://www.w3.org/WAI/tutorials/images/complex/)

## 수용 기준 (Acceptance Criteria) — 검증 가능한 형태로

- **AC-01:** 유효한 골격근량·체지방률 기록이 각각 2개 이상이면 인바디 영역에 `골격근량(kg)`과 `체지방률(%)` 카드가 별도로 표시되고 각 카드에 선과 측정점이 보인다.
- **AC-02:** 날짜가 뒤섞인 10개 기록을 주입하면 각 지표는 유효한 최신 8개만 선택해 날짜 오름차순으로 표시하며 입력 배열은 변경되지 않는다.
- **AC-03:** 한 지표가 누락된 기록은 해당 지표의 점에서만 제외되고 다른 지표와 몸무게 그래프에는 영향을 주지 않는다.
- **AC-04:** 유효 기록 0개에서는 해당 카드에 `기록이 없어요.`가 표시되고, 1개에서는 중앙 마커와 최신값이 표시된다.
- **AC-05:** 모든 값이 같은 기록 및 잘못된 가져오기 데이터에서도 DOM/SVG에 `NaN`, `Infinity`, 깨진 좌표가 생성되지 않는다.
- **AC-06:** 기록 추가, 같은 날짜 덮어쓰기, 삭제 후 페이지 새로고침 없이 그래프·최신값·최솟값·최댓값이 갱신된다.
- **AC-07:** 한국 표준시를 포함한 UTC±12 이상의 테스트 환경에서 오늘 날짜와 기록 날짜가 하루 앞뒤로 바뀌지 않는다.
- **AC-08:** 각 그래프는 스크린 리더가 지표명, 기간, 첫값, 최신값을 식별할 수 있고 원자료 기록 목록에 접근할 수 있다.
- **AC-09:** 라이트·다크 모드 및 320px~768px 뷰포트에서 선·마커가 식별 가능하고 가로 스크롤이 발생하지 않는다.
- **AC-10:** 신규 npm/CDN 의존성, 외부 네트워크 요청, `api/**`·DB·동기화 계약 변경이 없다.
- **AC-11:** 단위·통합 테스트와 저장/수정/삭제 E2E 시나리오가 통과하고 신규·변경 차트 로직의 line/branch/function coverage가 각각 80% 이상이다.
- **AC-12:** PR에는 이 기능과 테스트·필수 협업 문서 갱신만 포함되며 `1120d27`의 무관한 변경을 함께 가져오지 않는다.

## 예상 리스크

- **기준 브랜치 불일치:** `main`에는 인바디 모듈이 없고 현재 기능 브랜치에는 이미 프로토타입이 있어 잘못된 기준에서 작업하면 기능 전체가 한 PR에 섞인다. 기준 브랜치 확정을 구현 게이트로 둔다.
- **희소·부분 데이터:** 골격근량과 체지방률은 선택 입력이므로 두 그래프가 서로 다른 날짜 집합을 가질 수 있다. 지표별 유효 기록을 독립적으로 처리한다.
- **축 왜곡:** 작은 변화가 과장돼 보일 수 있다. 최솟값·최댓값과 단위를 항상 노출하고 의료적 해석 문구는 추가하지 않는다.
- **시간대 오류:** UTC 기반 날짜 생성·파싱은 날짜를 하루 이동시킬 수 있다. 저장된 날짜 키를 로컬 달력 문자열로 취급한다.
- **접근성 퇴행:** SVG를 `aria-hidden`으로만 처리하면 추이 정보가 스크린 리더에서 사라질 수 있다. 텍스트 요약과 기록 목록을 함께 제공한다.
- **대량 기록 성능:** 전체 기록을 매번 그리면 모바일에서 점이 뭉치고 렌더 비용이 증가한다. 지표별 최신 8개로 제한한다.
- **민감정보 노출:** 체성분은 건강정보다. 새 분석·로그·외부 전송을 추가하지 않고 기존 계정별 저장·동기화 경계 안에서만 처리한다.
- **기존 동기화 충돌:** 서버 동기화는 JSON 전체를 last-write-wins로 저장한다. 이번 PR에서는 이 정책을 변경하지 않으며 동시 다중 기기 편집 문제는 별도 작업으로 남긴다.
