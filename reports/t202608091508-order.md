## 목표

- 로그인 사용자가 **달력 화면**에서 완료된 운동 기록을 기준으로 최근 **6주간 주간 운동 볼륨**을 오래된 주부터 현재 주까지 막대그래프로 확인하게 한다.
- 볼륨 정의는 기존 규칙인 `완료 세트의 무게 × 횟수 합계`를 사용한다.
- 주차 기준은 기존 달력과 동일한 **일요일~토요일, 사용자 로컬 시간**으로 통일한다.
- 담당은 `[FE]`이며 브랜치는 `fe/weekly-volume-trend`로 한다. `api/**`와 DB는 변경하지 않는다.
- PR 범위는 주간 차트 하나로 제한한다. 최근 7일 요약, 운동별 성장 비교, 기간 필터, 목표 추천, Chart.js 도입은 제외한다.
- 선행 조건: 기존 [PR #1](https://github.com/osm0401/gmymate/pull/1)에 같은 기능이 다른 리팩터링과 묶여 있으므로, 해당 구현을 분리하거나 제거한 뒤 전용 PR을 만든다. `5007997` 또는 `32f66ff` 전체 cherry-pick은 금지한다.

## 리서치 근거 (검색으로 확인한 사실 + 왜 이 방식을 택했는지)

- 현재 체크아웃 `feature/t202608091508`과 `origin/main`에는 차트가 없지만, 로컬 `main`과 `fe/frontend-refactor`에는 `getWeeklyVolumeBuckets`, `renderWeeklyVolumeChart`, `#weeklyVolumeChart`가 이미 존재한다. 공개 PR도 이 구현이 **7개 커밋의 프런트엔드 리팩터링·협업 스캐폴드와 함께 묶여 있음**을 보여준다. 따라서 새로 설계하기보다 기존 코드를 참고해 차트 부분만 독립시킨다. [gmymate PR #1](https://github.com/osm0401/gmymate/pull/1)
- 선행 구현은 월요일을 주 시작일로 사용하지만 기존 `renderWeekStrip()`은 일요일부터 시작한다. 같은 화면에서 주 경계가 달라지는 오류를 막기 위해 일요일 시작으로 통일한다.
- Hevy는 총 볼륨·세트·운동 횟수를 기간별 차트로 제공하고, 주간 위젯에서는 현재 주와 이전 주를 비교한다. Strong도 주간 운동량과 운동별 추이를 프로필 대시보드에 배치한다. 따라서 활성 운동 화면보다 **달력·기록 화면에 집계 차트를 두는 방식**을 택한다. [Hevy 통계](https://help.hevyapp.com/hc/en-us/articles/35702030346903-Hevy-Statistics-Explained-Track-Your-Training-Progress-and-Muscle-Growth), [Hevy 주간 위젯](https://help.hevyapp.com/hc/en-us/articles/36956630666647-Hevy-App-Widgets-Explained-Setup-Features-and-How-to-Use-Them), [Strong 프로필 위젯](https://help.strongapp.io/article/239-profile-widgets)

- 2026-08-10 기준 Chart.js 최신 릴리스는 **v4.5.1**이며 Chrome 줌에서 차트가 축소되는 문제의 수정도 포함한다. Chart.js 4는 ESM 중심이고, 시간 축에는 별도 날짜 어댑터가 필요하며, v4에서 여러 API와 배포 파일이 제거·변경됐다. 빌드 도구와 패키지 매니페스트가 없는 이 저장소의 6열 그래프에는 의존성 비용이 더 크므로 기존처럼 HTML/CSS로 직접 구현한다. [v4.5.1 릴리스](https://github.com/chartjs/Chart.js/releases/tag/v4.5.1), [통합 문서](https://www.chartjs.org/docs/latest/getting-started/integration.html), [v4 마이그레이션](https://www.chartjs.org/docs/latest/migration/v4-migration.html)
- Chart.js 2.9.4 미만에는 프로토타입 오염 취약점 CVE-2020-7746이 있었다. 런타임 의존성을 추가하지 않으면 레거시 CDN 버전이나 공급망 위험도 피할 수 있다. [NVD CVE-2020-7746](https://nvd.nist.gov/vuln/detail/CVE-2020-7746)
- 시각 정보만으로 값을 전달하지 않도록 각 주차의 정확한 값을 의미론적 목록 또는 보조 데이터 표로 제공한다. W3C도 차트의 대체 표현으로 구조화된 데이터 표를 권장한다. [W3C 데이터 표 지침](https://www.w3.org/WAI/tutorials/tables/)

## 예상 리스크

- 현재 체크아웃, 로컬 `main`, `origin/main`, `fe/frontend-refactor`가 서로 크게 갈라져 있다. 기준 브랜치를 확정하지 않으면 IIFE와 ES 모듈 패턴이 섞이거나 중복 구현될 수 있다.
- 기존 PR #1은 주간 차트 외의 백엔드 WIP·협업 스캐폴드·대형 리팩터링을 포함한다. 전체 merge/cherry-pick은 단일 기능 PR 원칙을 깨뜨린다.
- 진행 중인 현재 주와 완료된 이전 주를 직접 비교하면 주초에 급감한 것처럼 보일 수 있다. 이번 PR에서는 증감률을 제외한다.
- 맨몸·유산소 운동은 현재 `무게 × 횟수` 정의상 `0kg`이 될 수 있다. 종목별 볼륨 정의 변경은 별도 제품 결정으로 둔다.
- 히스토리가 최대 80개 세션으로 잘리므로 매우 높은 운동 빈도에서는 6주 합계가 불완전할 수 있다.
- 날짜 문자열을 UTC로 파싱하면 한국 시간대나 DST 지역에서 주차가 이동할 수 있다. 로컬 날짜 파싱과 경계 테스트가 필수다.
- Chart.js를 후속 작업에서 도입한다면 v2 레거시 CDN을 금지하고 v4.5.1 이상 고정, 날짜 어댑터와 마이그레이션 변경점을 별도로 검토해야 한다.
- Node의 CLI 커버리지 임계값은 Node 22.8 이상이 필요하다. 리뷰 환경 버전을 먼저 확인한다.
